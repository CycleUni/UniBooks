# 期末收書・贈書活動：完整構想

狀態：構想第 2 版，尚未開發。確認後再依「分期」逐項實作。

第 2 版的變更：
- 新增學生會會員名冊匯入，配發時會員優先。
- 收書時用學號比對科系；比對不到時從科系下拉選單選，選單含「其他」。
- 呈現方式：書目頁把學生會的書合併成一筆並置頂，一般刊登照舊。
- 會員優先只限已驗證學號，領取不需核對學生證。

## 1. 目標與名詞

學生會在期末向學生**收書**，之後在學期初把書**贈送**給需要的學生。

| 名詞 | 意思 |
|---|---|
| 組織（organization） | 一個學校的一個學生組織，例如「致理科技大學 學生會」。書的「賣家」顯示它 |
| 會員名冊（roster） | 組織匯入的會員學號、姓名、科系、年級；配發時會員優先 |
| 收書活動（book drive） | 組織辦的一次收書加贈書，有收書、登記、配發、領取四個階段 |
| 書本（copy） | 收進來的一本實體書，有自己的書架編號與狀態 |
| 登記（claim） | 學生對「某一本書（書目）」表示想領，不針對某一本實體書 |
| 配發 | 登記結束後依會員身分、科系、年級排優先序，把實體書分給登記者 |

## 2. 角色與權限（三層，由上往下指派）

1. **站方管理員**（現有 `admin`，或負責該地區的 `staff`）在活動系統的「學生組織」頁（`/event/admin/orgs`）建立組織（學校加組織名），並指派**組織管理員**帳號（用 email 找帳號）。收書贈書的後台全部集中在活動系統，主站後台只負責二手書市集。
2. **組織管理員**（學生會的窗口）在活動系統管理會員名冊、建立自己組織的活動，並**依活動**指派**活動人員**。組織管理員自動擁有該組織所有活動的權限。
3. **活動人員**只能操作被指派的活動：收書上架、領取核對。不能改活動設定、不能跑配發、不能指派人、看不到名冊。

| 動作 | 站方 | 組織管理員 | 活動人員 |
|---|---|---|---|
| 建組織、指派組織管理員 | ✔ | | |
| 匯入、編輯會員名冊 | | ✔ | |
| 建立、編輯、關閉活動 | | ✔ | |
| 指派活動人員 | | ✔ | |
| 收書上架、編輯書本 | | ✔ | ✔ |
| 收書時以學號查科系 | | ✔ | ✔（只回科系） |
| 執行配發、處理放棄與遞補 | | ✔ | |
| 領取核對、現場發放 | | ✔ | ✔ |

組織管理員與活動人員不需要是站方 `staff`，一般帳號就可以。他們只在被指派的範圍內看得到後台。活動系統的其他頁面（抽獎）維持原本的 `staff` 權限，兩邊互不影響。

## 3. 架構決定：資料放主站，活動系統是它的後台介面（已確認）

活動系統目前有自己的 D1，不讀主站資料表，只透過 `MAIN` service binding 問「誰登入了」。收書贈書**不比照抽獎活動放在活動系統的 D1**，原因：

- 找書頁、書目頁、帳號頁、通知（信件與推播佇列）、學校與科系資料、學號驗證、書目 ISBN 查詢、成員 QR 全部在主站。放在活動系統，就得複製這些東西，或讓兩個 Worker 互相呼叫，形成循環。
- 「誰是組織管理員、誰是活動人員」要由主站判斷，才能保護主站的 API。做法和現有 `managed_regions` 相同：由 `/api/v1/auth/me` 回傳，頁面與 API 都以它為準。

因此：

- **主站**：新增資料表與 `/api/v1/orgs/*`、`/api/v1/drives/*` API，所有規則（權限、配發、領取、通知）都在這裡。
- **活動系統**：只新增 Astro 頁面與前端腳本。頁面和主站同源（`unibooks.app`），直接帶使用者自己的 cookie 呼叫主站 API。**不改活動系統的 D1，也不新增 Worker API**，現有抽獎活動一行不動。
- 活動系統的活動列表多一種收書活動卡片，連到主站的活動頁。登記介面只做一份，放在主站。

## 4. 資料模型（主站 migration `0010`）

```
organizations          id, region_code, school_id, name, is_active, created_at
organization_admins    organization_id, user_id                         (PK 兩欄)
organization_members   organization_id, student_number, name, department, grade,
                       valid_until, import_batch, created_at, updated_at
                       unique(organization_id, student_number)
book_drives            id, organization_id, region_code, title, description,
                       status (draft|intake|claiming|allocated|pickup|closed),
                       claim_opens_at, claim_closes_at, pickup_starts_at, pickup_ends_at,
                       max_claims_per_user (預設 3), member_priority (預設開),
                       allocation_seed, allocated_at, created_by, created_at
book_drive_staff       drive_id, user_id, added_by                       (PK 兩欄)
drive_copies           id, drive_id, book_id, shelf_code, condition,
                       donor_student_number, donor_department,          (僅活動人員可見)
                       target_department, target_grade,                 (這本書適用的科系與年級)
                       status (in_stock|allocated|picked_up|withdrawn),
                       claim_id, intake_by, created_at, picked_up_at, picked_up_by
drive_claims           id, drive_id, book_id, user_id,
                       student_number (僅已驗證學號，否則空), department, grade,
                       is_member, score, rank,
                       status (registered|won|waitlisted|not_won|picked_up|forfeited|cancelled),
                       copy_id, created_at, updated_at
                       unique(drive_id, user_id, book_id)
```

科系欄位一律存**文字**：選單選到的就存科系正式名稱，選「其他」就存手填文字。這樣清單改名或缺漏都不會讓舊資料失效。比對時一律用現有的科系正規化規則（台讀作臺、學系讀作系、比對別名），所以手填的「資管」也能對上「資訊管理學系」。

重用而非新增的部分：

- `books`：書目、封面、ISBN 查詢，與刊登共用。
- `schools`：顯示校名，含各語言名稱。
- `categories.departments`：科系清單與別名。
- `student_id_verifications`：已通過的學號驗證。
- `regionVerifications`：登記者須通過該地區的學校驗證。
- `audit_events`：所有人員操作留稽核。
- 學號正規化：現在寫在 `routes/accounts.ts` 裡（去空白、轉大寫、`^[A-Z0-9-]{4,20}$`），抽成 `lib/studentNumber.ts` 共用，學號驗證、名冊、收書、登記四處都走它。這是把既有邏輯原樣搬出去，不改行為。

**不放進 `listings`**：贈書沒有價格、買家、訂單、聊天，一本書也不是單一賣家的一筆刊登。硬塞進去，`orders`、`conversations`、搜尋都要加例外。獨立資料表加共用書目，兩邊都不必改。

## 5. 流程

### 5.1 會員名冊（組織管理員，活動系統）

- **匯入**：上傳 CSV，或直接從試算表複製貼上。欄位有學號（必填）、姓名、科系、年級、有效期限（預設本學年結束）。欄位順序可在匯入畫面對應。
- **預覽後才寫入**：逐列標出格式錯誤、重複學號、科系對不上清單的列（對不上的科系照存為文字，只是提醒）。確認後才寫入。
- **兩種模式**：
  - 「新增與更新」：同學號覆蓋。
  - 「整份取代」：換屆時用，未出現在新名冊的會員移除。
- **其他操作**：可單筆新增、編輯、刪除，也可搜尋。過期會員不算會員，由排程刪除。
- **個資**：名冊只有該組織的組織管理員看得到。活動人員收書時查學號，只拿到科系與年級，看不到姓名，也不能列出名冊。

### 5.2 收書（活動人員，活動系統，現場填）

- 掃 ISBN 條碼（沿用活動系統現有的掃描元件）或手輸。書目走主站既有的 ISBN 查詢與建立流程，查不到可手動建（沿用 `manual` 書目與審核）。
- **輸入捐書人學號後自動帶科系**，依序比對：
  1. 本組織會員名冊。
  2. 已通過的學號驗證（該校）中，該學號的帳號。這一步只拿來推科系，不顯示帳號。
  3. 本組織以前活動中，同一學號的收書紀錄。
- **比對不到**：從**科系下拉選單**選。選單依學院分組，可打字搜尋（別名也找得到），最後一項是**「其他」**，選了會出現文字欄自填。
- 每本填：
  - 品相。
  - 這本書的適用科系與年級：預設帶捐書人的科系，可改，選單同上，同樣有「其他」。
- 「再收一本」一鍵沿用上一筆的捐書人與科系，同一位學生一次捐很多本時很快。
- 每本自動產生書架編號（A-001…），貼在書上，領取時照編號找書。
- 書可以編輯、可以下架（`withdrawn`，例如破損）。已配發的書不能直接下架，要先取消那筆配發。
- 捐書人學號與科系只有活動人員看得到，公開 API 一律不回。活動結束 30 天後由排程清空這兩欄。

### 5.3 顯示（主站）

- **書目頁 `/book`**：
  - 該書有進行中的贈書時，**最上方置頂一筆**「致理科技大學 學生會」（校名依頁面語言顯示，後面接組織名），寫「贈書・剩 3 本・N 人登記」，按鈕是**「登記領取」**。
  - 不論學生會收了幾本，都只顯示這一筆，不列出各本，也不能挑哪一本。
  - 同一本書有多個組織各自辦活動時，每個組織一筆，都置頂。
  - 下方的一般二手書刊登照原本方式逐筆顯示，聯絡方式仍是私訊，完全不動。
- **找書結果**：書目卡片多一個「學生會贈書」標記，點進書目頁就看到置頂那一筆。搜尋與排序邏輯不動。
- **活動頁 `/<region>/drive?id=`**：列出這次活動所有書目，每個書目一張卡，附剩餘本數與登記按鈕。活動系統的活動列表連到這裡。
- 贈書預設不開放挑選，也不依品項登記，只依書目登記。日後若要開放挑選，就是讓 `drive_claims.copy_id` 在登記時先指定，資料表不需要改。

### 5.4 登記（學生，主站）

- **條件**：已登入、通過該地區的學校驗證、活動在登記期間。
- **填寫**：
  - **學號**：只採用帳號在該校**已通過的學號驗證**（站方審核學生證的既有功能），自動帶入、不能改。沒有驗證的人不填學號，照樣可以登記。
  - **科系**：有已驗證學號就先比對名冊帶入；比對不到或沒有學號，就用與收書同一份下拉選單，含「其他」。
  - **年級**：名冊有就帶入，否則自選。
- **會員判定**：**只有已驗證學號**且學號在名冊內、未過期，才算會員。
  - 沒有學號驗證的人以非會員身分參加配發。登記頁會提示「完成學號驗證，會員可優先配發」，並連到主站既有的學號驗證頁。
  - 會員身分在配發當下判定：登記後、截止前才通過驗證的人也算。
  - 領取時不需要現場核對學生證，學號已由站方審核過。
- **上限與取消**：每人每本書只能登記一次，總共最多 `max_claims_per_user` 本。登記期間內可以取消，也可以改資料。
- **帳號頁**：新增「領書登記」分頁，列出登記清單與狀態。
- **不先佔書**：登記時還不知道誰拿到，所以登記人數可以超過庫存，頁面顯示「N 人登記」。

### 5.5 配發（組織管理員，活動系統）

登記截止後先按「試算」，檢視結果後再按「確認配發」。確認前不寫入任何資料。

每本書的登記者依下列順序排優先，比完一層才比下一層：

1. **會員**：學號已驗證且在名冊內的會員優先（活動可關閉這一層）。
2. **科系**：與這本書的適用科系相同 > 同學院 > 其他。書沒有指定科系時，所有人同分。選「其他」手填的科系，用正規化後的文字比對。
3. **年級**：與適用年級相同 > 相差一級 > 其他。
4. **同分**：用活動的公開種子隨機排序（`allocation_seed`），不看登記先後，避免變成搶快。用同一個種子重算，結果會完全相同，可以稽核。

依全體登記者的優先順序逐筆處理：

- 每本書的前 N 名得書（N 是該書本數），但每人總數不超過 `max_claims_per_user`。
- 其餘的人列為「候補」並有候補順位，排不進候補的是「未配到」。
- 配發在一個交易內寫完登記狀態、實體書狀態與 `copy_id`。重按一次結果不變。

試算畫面每本書會列出排名與排名原因（會員、科系、年級各符不符合），方便學生會回答「為什麼我沒拿到」。

結果以信件加推播通知：
- 得書：附領取時間與地點，並提醒用成員 QR 領取。
- 候補。
- 未配到。

### 5.6 領取與已領書管理（活動人員，活動系統）

- **領取**：
  - 學生出示**成員 QR**（現有的 member pass，不新增憑證），人員掃描後畫面列出這位學生配到的書與書架編號，逐本核對後標記「已領取」。
  - 掃不到 QR 時，可以用學號或 email 搜尋。
- **書的狀態**：`in_stock → allocated → picked_up`，`withdrawn` 是下架。標錯可由組織管理員還原。每次狀態變動都寫稽核。
- **管理看板**（每個書目一列）：本數、登記人數、已配發、已領取、放棄、剩餘。可依狀態篩選、匯出清單。
- **逾期未領**：
  - 領取期限到時，得書者標為 `forfeited`，書回到庫存。
  - 依候補順位自動遞補並通知。遞補者另有 24 小時領取（活動可調）。
  - 還有剩書時，活動可以改成**現場發放**：到場者掃成員 QR 就能領，系統同樣建立登記與領取紀錄，所以每一本送出去的書都有收件人。
- **結束活動**：未領的書可以留在原活動，或轉入下一次活動（書搬到新活動，書架編號保留）。

## 6. 對現有程式的影響（確保不重構）

| 位置 | 變動 |
|---|---|
| 主站 DB | 新 migration 只加表，既有表不改欄位 |
| `/auth/me` | 新增 `organizations`（我管理的組織）、`staffed_drives`（我被指派的活動），與 `managed_regions` 並列 |
| `routes/accounts.ts` 學號驗證 | 學號正規化改呼叫抽出的 `lib/studentNumber.ts`，行為不變 |
| 主站書目頁 | 上方多一個置頂區塊；一般刊登的列表元件不動 |
| 主站找書結果 | 書目卡片多一個標記；搜尋與排序不動 |
| 活動系統 `lib/auth.ts` | `AuthUser` 多兩欄。新頁面用 `canManageDrive` 判斷權限，抽獎頁仍用 `isStaff` |
| 活動系統 D1、`api.ts` | 不動 |
| 主站 `listings`、`orders`、聊天 | 不動 |
| 通知 | 走現有的信件與推播佇列，比照 `deliverNotices` 的模式，加新文案（zh-TW、zh-HK、en） |
| 稽核、地區範圍、速率限制、錯誤格式 | 全部重用現有 helper |

DRY 的具體做法：

- **優先序計算只寫一份**：主站 `services/drives/priority.ts`，是純函式並附測試，回傳排名與原因。前端只顯示後端給的結果，不另外實作。
- **權限判斷只寫一份**：`services/drives/access.ts` 提供 `assertDriveRole(user, drive, 'staff'|'admin')` 與 `assertOrgAdmin(user, org)`，所有端點共用，寫法比照 `services/admin/scope.ts`。
- **學號轉科系只寫一份**：`services/drives/studentLookup.ts`，依名冊、學號驗證、過往收書的順序比對。收書與登記兩處共用。
- **科系選單元件**：
  - 主站一份（Angular），活動系統一份（Astro 前端腳本），兩邊都讀主站同一支 API 拿科系清單，最後一項都是「其他」。
  - 科系比對規則只在主站後端，前端不重寫。
- **學號正規化**只放在 `lib/studentNumber.ts`。
- **狀態轉換表**集中在一處，寫法比照 `services/orders/transitions.ts`，端點與排程都走它。

## 7. 分期（每期一個功能 commit，兩個 repo 各一）

1. **組織、權限與名冊**：`organizations`、`organization_admins`、`organization_members`、活動系統的組織管理頁、`/auth/me` 擴充、活動系統依權限顯示導覽、名冊匯入頁、`lib/studentNumber.ts`。
